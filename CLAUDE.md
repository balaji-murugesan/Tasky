# Tasky — agent operating manual

Tasky is a small todo app (React + Express) that exists to practise an **autonomous delivery loop**.
Read this file fully before changing anything.

## The loop (what every change goes through)

```
request (issue / chat / email)
  → /openspec-propose          spec delta + design + tasks       (planning only)
  → /openspec-apply-change     code + tests                      (implementation)
  → npm run verify             typecheck + unit + e2e            (must be green)
  → screenshot-changes skill   PNGs of affected screens          (evidence)
  → open PR                    spec link + screenshots + risk    (review surface)
  → CI re-verifies, classifies risk, auto-merges if low          (gate)
  → post-merge: openspec archive                                 (specs updated)
```

## Commands

| Task | Command |
|---|---|
| Install | `npm ci` |
| Start app (background, idempotent) | `npm run app:up` → http://localhost:5173 |
| Stop app | `npm run app:down` |
| App logs | `bash scripts/run-app.sh logs` |
| Typecheck | `npm run typecheck` |
| Unit/API tests | `npm test` |
| E2E tests | `npm run e2e` |
| Everything | `npm run verify` |
| Screenshots | `npm run screenshots` (app must be up) |
| Risk of current branch | `npm run risk -- origin/main` |
| Specs | `npx openspec list --specs`, `npx openspec validate --all` |

If Playwright's bundled browser is unavailable, prefix with `PW_CHANNEL=chrome`.

## Definition of Done

A change is done only when ALL are true:
1. An OpenSpec change exists under `openspec/changes/<id>/` and `npx openspec validate <id>` passes.
2. Every scenario in the spec delta is covered by a test (Vitest for API, Playwright for UI).
3. `npm run verify` is green locally.
4. If any screen changed, `screenshots.config.json` covers it and `npm run screenshots` succeeded.
5. The PR body uses `.github/pull_request_template.md` and includes the risk output.

## Rules

- **One change per PR.** Branch name: `agent/<openspec-change-id>`.
- **Never edit high-risk paths** (see `risk-policy.json` → `high`) unless the issue carries the label `agent:allow-high-risk`. Those PRs never auto-merge.
- **Don't weaken tests to make them pass.** If a test is wrong, say why in the PR.
- **Don't add dependencies** without the issue asking for it (package.json is high risk).
- **Unattended runs cannot ask questions.** If blocked or the spec is ambiguous: commit what you have, open the PR as draft, put the question at the top of the body, and add the label `needs-human`.
- Keep UI selectors accessible (labels/roles). Tests and screenshots rely on `getByLabel` / `getByRole`.

## Project skills (in `.claude/skills/`)

- `run-app` — boot, health-check, debug and stop the app.
- `screenshot-changes` — capture screens affected by a diff and attach them to the PR.
- `app-qa` — exploratory QA of the running app; files deduplicated bug issues.
- `intake-to-issue` — turn a chat message or email into a ready-to-build GitHub issue.
- `ship-change` — the whole loop end-to-end for one issue (propose → apply → verify → screenshots → PR).
- `openspec-*` — generated by `openspec init`; don't edit, run `npx openspec update` instead.

## Labels used by automation

| Label | Meaning |
|---|---|
| `agent:ready` | Issue is specified enough for an agent to build tonight |
| `agent:building` | An agent run has claimed it |
| `risk:low` / `risk:medium` / `risk:high` | Set by CI from `risk-policy.json` |
| `needs-human` | Agent is blocked or unsure — never auto-merged |
| `do-not-merge` | Hard stop |
| `source:chat` / `source:email` / `source:qa` | Where the request came from |
